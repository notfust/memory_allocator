# Архитектурные решения

## Назначение документа

Этот документ фиксирует причины решений, реализованных в текущем
`memory_allocator`. Он описывает учебный standalone-аллокатор на C99 для
разработки на host и последующей адаптации к Infineon AURIX TC397XA. Решения,
помеченные как ограничения, не следует считать окончательным контрактом для
production-интеграции.

## Отсутствие зависимости от libc

**Решение:** использовать собственные функции `memory_init`, `memory_alloc` и
`memory_free`; не вызывать `malloc`, `calloc`, `realloc` и `free`.

**Причина:** целевая embedded-среда может не иметь доступного либо приемлемого
по времени и потреблению памяти libc heap. Явная реализация позволяет
контролировать размер heap, расположение metadata и алгоритм освобождения.

**Отклонено:** использование системного аллокатора или аллокатора RTOS как
обязательной части компонента.

**Следствие:** компонент остаётся переносимым и не требует ОС, но сам отвечает
за управление фрагментацией и проверку корректности операций.

## Статический heap фиксированного размера

**Решение:** текущая версия хранит heap размером 2048 байт во внутреннем
статическом объекте.

**Причина:** это делает прототип самодостаточным: он не запрашивает память у
внешнего аллокатора и не зависит от этапа запуска платформы.

**Отклонено:** выделение heap динамически при инициализации.

**Ограничение:** фиксированный singleton-heap не выражает ownership и плохо
подходит для реальной интеграции. Целевой дизайн должен принимать внешний
memory region через context аллокатора; platform layer будет выбирать linker
section, размер и время инициализации.

## Неявный список физических блоков

**Решение:** хранить заголовок непосредственно перед payload каждого блока и
связывать блоки полями `next` и `prev`.

**Причина:** metadata размещается внутри заранее выделенного heap и не требует
внешней памяти. Двусвязность позволяет при освобождении объединять блок с
предыдущим соседом без отдельного поиска предыдущего элемента.

**Отклонено:** отдельный список узлов, память для которого выделяется
динамически.

**Следствие:** metadata уменьшает доступный payload. Кроме того, повреждение
пользовательских данных может повредить следующий заголовок, поэтому для
production-API нужны строгая валидация указателя и диагностические проверки.

## First-fit для выбора свободного блока

**Решение:** при выделении последовательно искать первый свободный блок,
достаточный для запроса.

**Причина:** алгоритм прост, компактен, не требует дополнительных таблиц или
списков классов размеров и удобен как базовая реализация для host-разработки.

**Отклонено:** best-fit, TLSF, segregated free lists и более сложные схемы
индексации свободных блоков.

**Следствие:** выделение имеет сложность O(n) в худшем случае и может создавать
внешнюю фрагментацию. Поэтому текущая схема не заявляется как hard real-time
решение: пригодность для radar workload должна подтверждаться измерениями
worst-case latency, RAM и фрагментации на TC397XA.

## Разделение и объединение блоков

**Решение:** большой свободный блок разделяется при allocation, а соседние
свободные блоки объединяются при `memory_free`.

**Причина:** split уменьшает внутренние потери памяти для малых запросов, а
локальное coalescing возвращает крупные непрерывные области и ограничивает
накопление внешней фрагментации.

**Отклонено:** выдача целого подходящего блока без разделения и отложенное
полное объединение только отдельным проходом.

**Следствие:** освобождение изменяет metadata соседей. Остаток после split
создаётся лишь тогда, когда в нём поместятся заголовок и минимальный полезный
payload; иначе выделяется весь исходный блок.

## Выравнивание payload в рамках C99

**Решение:** platform-конфигурация в `memory_allocator_platform.h` задаёт
`MEMORY_ALLOCATOR_ALIGNMENT`. Начало внутреннего heap выравнивается
C99-совместимым union, а размер каждого payload и padded-размер заголовка
округляются до этого контракта. Публичный `memory_allocator.h` не содержит
TriCore-условий.

**Причина:** одного выравнивания начала массива недостаточно: каждый следующий
заголовок и возвращаемый указатель также должны удовлетворять контракту
выравнивания. C11 `_Alignas` не используется, так как проект ограничен C99.

**Отклонено:** обычный `uint8_t`-массив без wrapper-типа, выравнивание только
размера запроса и безусловное применение C11 либо compiler-specific атрибутов.

**Следствие:** для target-конфигурации `TRICORE_TARGET` контракт задан как
4 байта согласно предположению о TriCore EABI; на host используется C99 offset-probe alignment wrapper с набором стандартных
скалярных типов, а не размер union. Target-контракт необходимо
подтвердить сборкой и тестом на `tricore-gcc`.

Metadata не интерпретируется через приведение `uint8_t *` к
`memory_block_t *`. Header сначала копируется из byte region в локальный
`memory_block_t`, а после изменения копируется обратно функцией
`memory_copy_bytes()`. Это эквивалентно ограниченному локальному `memcpy`, но
не зависит от libc: копируются представления объектов по одному `uint8_t`.
Побайтный доступ разрешён C99, а локальный объект `memory_block_t` создаётся
обычным способом, поэтому allocator не обращается к `uint8_t[]` как к объекту
несовместимого типа.

## Минимальный публичный API

**Решение:** текущий интерфейс содержит только инициализацию, выделение и
освобождение памяти.

**Причина:** малый API упрощает интеграцию и не создаёт скрытых механизмов
владения, статистики или callback-ов в базовом прототипе.

**Отклонено:** добавление зависимостей от ОС, исключений, неявного глобального
кода ошибки и автоматического расширения heap.

**Ограничение:** `memory_free` пока не возвращает статус, поэтому не способен
сообщить вызывающему коду о некорректном указателе или повторном освобождении.
При переходе к context-based API необходимо добавить явные status codes и
документировать ownership, повторную инициализацию, concurrency и правила ISR.

## Безопасная арифметика размеров

**Решение:** все операции, которые формируют выровненный размер либо складывают
размер header и payload, выполняются через C99-предикат переполнения.
Специализированная внутренняя функция выравнивает размер только по единственному
compile-time контракту `MEMORY_ALLOCATOR_ALIGNMENT`; параметр выравнивания не
передаётся вызывающим кодом. `memory_alloc` отклоняет запрос, если округление не
помещается в `size_t`; `memory_free(NULL)` возвращается до любой адресной
арифметики. Слияние соседних блоков также записывает metadata только после
успешной проверки суммы.

**Причина:** некорректно округлённый большой запрос мог превратиться в маленький
размер, а непроверенное сложение при split/coalesce — выйти за пределы heap.
Предикаты не используют libc, не выделяют память и имеют постоянную стоимость.

**Ограничение:** проверка принадлежности произвольного указателя heap, защита от
double free и forged/interior pointer требуют отдельной валидации списка и не
входят в этот пункт backlog.

## Воспроизводимая host-проверка

**Решение:** GNU Makefile предоставляет цель `test-host`, которая собирает
allocator и host-тесты в строгом C99-режиме с предупреждениями. Цели `debug` и
`release` дают host-сборки с разными оптимизационными профилями, а также есть
необязательная цель `test-sanitize` для AddressSanitizer и
UndefinedBehaviorSanitizer. Цели `target-debug` и `target-release` используют
`tricore-gcc`, если этот toolchain доступен в окружении.

**Причина:** тесты должны запускаться одной воспроизводимой командой без IDE.
Это быстро выявляет регрессии арифметики размеров и выравнивания на host, не
добавляя зависимостей в embedded allocator.

**Ограничение:** sanitizer-инструменты применимы только в host-среде и не
заменяют сборку и испытания HighTec `tricore-gcc` на AURIX TC397XA. Target build
остается задачей интеграции platform layer.

## Изоляция платформенной специфики

**Решение:** core не обращается к регистрам MCU, ОС или linker symbols;
TriCore-специфика ограничена условной компиляцией alignment-контракта.

**Причина:** одна и та же алгоритмическая часть должна собираться на host для
быстрой отладки и на AURIX для целевой проверки.

**Отклонено:** распределение platform-specific условий по алгоритму выделения
и освобождения памяти.

**Следствие:** при развитии проекта platform layer должен стать единственным
местом, где определяются memory region, linker integration, startup и, при
необходимости, cache/MPU-настройки.

## Однопоточная модель

**Решение:** текущая реализация не использует блокировки и не является
безопасной для одновременного доступа из нескольких потоков, задач или ISR.

**Причина:** базовый embedded-прототип не должен неявно зависеть от примитивов
ОС или атомарных операций, а их стоимость и допустимость зависят от сценария
интеграции.

**Отклонено:** встроенная универсальная синхронизация.

**Следствие:** вызывать allocator можно только из одного контекста либо при
внешне обеспеченной сериализации. Требования к concurrency и ISR должны быть
отдельным архитектурным решением до production-использования.

## Что пока не принято

Не приняты окончательно выбор pool/arena/TLSF, формат диагностической
информации, защита metadata, многопоточность и стратегия размещения heap на
target. Их выбор должен опираться на профиль реальных allocations radar
tracking, допустимый WCET, бюджет RAM/flash и результаты измерений на
TC397XA, а не только на host-тесты.
