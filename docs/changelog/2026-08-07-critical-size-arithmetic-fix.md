# Critical: безопасная арифметика размеров и `NULL` в `memory_free`

**Статус:** завершён второй Critical-пункт из [`BACKLOG.md`](../../BACKLOG.md):
устранение undefined behavior для `memory_free(NULL)` и переполнений `size_t` в
расчётах `memory_alloc()`/`memory_free()`.

## 1. Как устроен allocator до этого изменения

Allocator использует внутренний heap размером 2048 байт и хранит перед каждым
выданным пользователю диапазоном служебный header `memory_block_t`. Поле `size`
в header — это размер payload, то есть число байтов, доступных пользователю. Для
каждого блока физическая схема памяти выглядит так:

```text
[ padded header ][ aligned payload ]
^                 ^
block_address     указатель, возвращаемый memory_alloc()
```

Размер header дополняется до `MEMORY_ALLOCATOR_ALIGNMENT`, а запрос пользователя
также округляется до этого значения. Это было реализовано первым Critical-пунктом
для сохранения корректного выравнивания.

При `memory_alloc()` allocator ищет первый свободный блок достаточного размера.
Если после выдачи payload остаётся достаточно места для нового header и
минимального payload, свободный блок разделяется (split) на занятый и новый
свободный. При `memory_free()` соседние свободные блоки объединяются
(coalesce), чтобы уменьшить внешнюю фрагментацию.

Все эти операции зависят от вычислений размеров. Поэтому даже при маленьком
физическом heap нельзя считать большие значения `size_t` безопасными: они
обрабатываются *до* того, как allocator сравнит запрос с доступными 2048 байтами.

## 2. Исправляемые недостатки

### 2.1. Переполнение при округлении запроса

До исправления функция выравнивания возвращала `size_t` напрямую. Ей
передавали alignment contract отдельным параметром:

```c
static size_t align_size(size_t size, size_t align)
{
    size_t remainder = size % align;
    return (remainder == 0) ? size : size + (align - remainder);
}
```

Например, при alignment 8 запрос `SIZE_MAX - 1` имеет остаток 6. Для округления
необходимо прибавить 2, но это больше максимального представимого `size_t`.
Для беззнакового типа результат вычисляется по модулю `SIZE_MAX + 1`, то есть
становится небольшим числом. Вместо корректного отказа allocator мог принять
практически максимальный запрос как маленький и выделить под него маленький
блок. Если вызывающий код затем использовал исходный большой размер, это вело бы
к выходу за границы выданного payload и повреждению heap.

### 2.2. Переполнение сумм header и payload

В исходном варианте несколько размеров складывались без проверки:

```c
return block_header_size() + data_size;

if (current.size > size + block_total_size(MIN_USEFUL_SIZE)) {
    /* split */
}

previous.size += block_total_size(block.size);
block.size += block_total_size(next.size);
```

Каждое из этих сложений имеет разные последствия:

- `header + payload` определяет физический размер выделяемого блока;
- `size + minimum_block_size` определяет, допустим ли split;
- суммы в coalesce определяют размер объединённого свободного блока.

Если переполнение не обнаружить, вычисленный размер становится меньше реального.
При split это может дать неверный адрес следующего header или неверный остаток.
При coalesce повреждённый либо крайний размер может записать слишком маленькое
значение в metadata и разрушить модель списка блоков.

В штатном непрерывном heap размером 2048 байт нормальные блоки не могут
достичь предела `size_t`. Проверки всё равно необходимы: они являются границей
безопасности между внешним размером запроса/повреждённой metadata и внутренней
арифметикой allocator.

### 2.3. Адресная арифметика над `NULL` в `memory_free`

Для освобождения allocator должен найти header, расположенный перед payload.
В старом коде это делалось до проверки аргумента:

```c
block_address = (uint8_t *)ptr - block_header_size();

if (ptr == NULL) {
    return;
}
```

Вычитание из нулевого указателя не определено стандартом C99. Даже если на
конкретной host-платформе программа обычно не падала, компилятор вправе считать,
что такой путь невозможен, и оптимизировать код исходя из этого предположения.
Для embedded-компонента это недопустимо: `memory_free(NULL)` должен быть
предсказуемым no-op, как и в обычном API освобождения памяти.

## 3. Внесённые изменения

### 3.1. Общий предикат безопасного сложения `add_sizes()`

Добавлена внутренняя функция:

```c
static bool add_sizes(size_t left, size_t right, size_t *result)
{
    if (result == NULL || left > (SIZE_MAX - right)) {
        return false;
    }

    *result = left + right;
    return true;
}
```

Проверка `left > SIZE_MAX - right` выполняется **до** сложения. Если она ложна,
математическая сумма гарантированно помещается в `size_t`, и операция
`left + right` безопасна. Это стандартный C99-приём: он не использует C11
built-in-функции компилятора, 64-битные временные типы или libc.

`result == NULL` также проверяется явно. В текущем allocator все внутренние
вызовы передают действительный адрес локальной переменной, однако проверка
делает контракт helper-функции полным и не создаёт скрытого undefined behavior.

### 3.2. `align_allocator_size()` теперь сообщает об ошибке

Функция изменила контракт: вместо возврата размера она возвращает `bool`, а
результат записывает через указатель.

```c
static bool align_allocator_size(size_t size, size_t *aligned_size)
{
    size_t remainder;

    if (aligned_size == NULL) {
        return false;
    }

    remainder = size % MEMORY_ALLOCATOR_ALIGNMENT;
    if (remainder == 0U) {
        *aligned_size = size;
        return true;
    }

    return add_sizes(size,
                     MEMORY_ALLOCATOR_ALIGNMENT - remainder,
                     aligned_size);
}
```

Теперь округление `SIZE_MAX - 1` до кратного 8 не возвращает обёрнутое малое
число: `add_sizes()` возвращает `false`, а `memory_alloc()` немедленно выдаёт
`NULL`. `MEMORY_ALLOCATOR_ALIGNMENT` задаётся platform-конфигурацией как
ненулевой compile-time contract; у helper нет внешнего параметра, который мог
бы передать ноль.

### 3.2.1. Упрощение после code review

В ходе независимого review было отмечено, что `align` не является переменным
параметром алгоритма: каждый вызов передавал
`MEMORY_ALLOCATOR_ALIGNMENT`, определяемый один раз для конкретной сборки.
Поэтому helper был переименован в `align_allocator_size()` и больше не принимает
`align`. Это исключило лишний аргумент и недостижимую при корректной
platform-конфигурации проверку `align == 0U`, не меняя алгоритм, ABI или
выравнивание payload.

Review также рекомендовал добавить воспроизводимый host-запуск тестов и явно
разделить debug/release-сборки для host и target. В корне проекта создан GNU Makefile
с целями `debug`, `release`, `test-host`, `test-sanitize`, `target-debug` и
`target-release`. Это относится к верификации уже выполненного Critical-пункта,
а не к защите от double free, forged pointer или interior pointer.

### 3.3. Безопасные `block_header_size()` и `block_total_size()`

`block_header_size()` и `block_total_size()` также переведены на контракт
«успех + результат»:

```c
static bool block_total_size(size_t data_size, size_t *total_size)
{
    size_t header_size;

    if (!block_header_size(&header_size)) {
        return false;
    }

    return add_sizes(header_size, data_size, total_size);
}
```

Это централизует расчёт физического размера блока. Вызывающий код больше не
выполняет `header + payload` вручную и не может случайно пропустить проверку
переполнения.

`memory_init()` проверяет расчёт padded header перед созданием первого блока.
В текущей конфигурации `sizeof(memory_block_t)` и alignment — compile-time
константы, поэтому этот путь не должен завершаться ошибкой. Проверка оставлена,
чтобы инициализация не создала некорректный heap, если platform configuration
будет изменена в будущем.

### 3.4. Безопасный split в `memory_alloc()`

До создания следующего блока `memory_alloc()` теперь:

1. безопасно выравнивает пользовательский запрос;
2. безопасно вычисляет минимальный физический размер потенциального остатка;
3. получает остаток вычитанием `current.size - size` только после проверки
   `current.size >= size`;
4. безопасно вычисляет физический размер выдаваемого блока;
5. только после успешных вычислений изменяет metadata и выполняет split.

Существенная часть логики выглядит так:

```c
if (!align_allocator_size(size, &size)) {
    return NULL;
}

if (!block_total_size(MIN_USEFUL_SIZE, &minimum_block_size)) {
    return NULL;
}

if (current.is_free && current.size >= size) {
    size_t remaining_size = current.size - size;

    if (remaining_size > minimum_block_size) {
        if (!block_total_size(size, &allocated_block_size)) {
            return NULL;
        }
        /* Создание split-блока. */
    }
}
```

Важно различать `remaining_size` и физический размер остатка. После выдачи
payload размером `size` остаток payload равен `current.size - size`; чтобы
создать из него самостоятельный блок, в нём дополнительно должен поместиться
новый padded header. Поэтому split возможен только при остатке больше
`header + MIN_USEFUL_SIZE`.

### 3.5. Безопасный coalesce в `memory_free()`

Для слияния двух блоков необходимо добавить к payload первого блока физический
размер второго, то есть `padded_header + second_payload`. Обе операции теперь
проверяются до изменения списка:

```c
if (!block_total_size(block.size, &block_size_with_header) ||
    !add_sizes(previous.size, block_size_with_header, &merged_size)) {
    return;
}
```

Та же схема применяется при слиянии с последующим соседом. Пока сумма не
проверена, изменяется только локальная переменная `block`; metadata heap не
записывается. При неуспехе функция возвращается без частичного освобождения или
частичной перестройки списка. Это особенно важно, поскольку `memory_free()`
имеет `void` API и не может сообщить вызывающему коду статус ошибки.

После всех успешных расчётов записывается объединённый header и при
необходимости обновляется `prev` у следующего физического блока. Флаг
`neighbours_changed` не даёт выполнять лишнюю запись в header следующего блока,
если объединения не было.

### 3.6. Ранний выход `memory_free(NULL)`

Порядок действий в `memory_free()` теперь следующий:

```c
if (ptr == NULL) {
    return;
}

if (!block_header_size(&header_size)) {
    return;
}

block_address = (uint8_t *)ptr - header_size;
```

То есть вычитание размера header выполняется только для ненулевого указателя.
Это устраняет именно UB для `NULL` и делает вызов no-op.

## 5. Почему выбран этот подход

Подход с маленькими внутренними helper-функциями выбран по следующим причинам:

- **C99-совместимость.** Используется только стандартный `SIZE_MAX` из
  `<stdint.h>`, обычное сравнение и `bool`; нет C11/C23 возможностей.
- **Нет libc и hidden allocation.** Проверки не используют `malloc`, `memcpy`,
  ОС или runtime-службы.
- **Единая точка контроля.** `add_sizes()` исключает дублирование опасного
  шаблона `a + b` в логике allocator.
- **Сохранение интерфейса.** Изменения изолированы внутри implementation и не
  требуют менять вызывающий код или ABI публичных функций.
- **Fail-safe поведение.** При невозможном расчёте allocation возвращает `NULL`,
  а освобождение не записывает частично вычисленную metadata.
- **Предсказуемая стоимость.** Все новые проверки имеют фиксированное число
  простых операций. Они не добавляют проход по списку блоков и не меняют
  алгоритм first-fit.

## 6. Рассмотренные альтернативы

### 6.1. Просто отклонять запросы больше 2048 байт

Такой ранний фильтр полезен как дополнительная оптимизация, но сам по себе не
решает проблему. Округление выполнялось до поиска блока, а будущий allocator с
внешним region может иметь размер значительно больше 2048. Кроме того, coalesce
работает с metadata, а не с исходным пользовательским запросом. Поэтому проверка
каждой операции сложения остаётся необходимой.

### 6.2. Считать, что переполнение невозможно из-за маленького heap

Не выбрано. Внешний `size` имеет тип `size_t` и может быть любым. Повреждённый
header также способен содержать крайнее значение. Корректность allocator не
должна зависеть от неявного предположения, что все входы уже безопасны.

### 6.3. Использовать `__builtin_add_overflow` или compiler-specific intrinsics

Не выбрано. GCC/Clang built-in может сделать код компактнее, но не является
стандартом C99 и его поведение/доступность необходимо отдельно подтверждать для
HighTec `tricore-gcc`. Проверка через `SIZE_MAX - right` одинакова для host и
целевого toolchain.

### 6.4. Выполнять вычисления в более широком типе

Не выбрано. На 32-битном TriCore `uint64_t` доступен как тип, но это не
универсальное решение: для `size_t` шириной 64 бита стандартный C99 не обещает
более широкий целый тип. Кроме того, 64-битная арифметика может быть дороже на
32-битном MCU и не заменяет явного результата «переполнение».

### 6.5. Использовать saturating arithmetic

Не выбрано. Насыщение до `SIZE_MAX` скрывает ошибку вычисления и создаёт
неоднозначную семантику: получившийся размер может выглядеть валидным. Для
allocator корректнее явно отказать в allocation или не менять metadata.

### 6.6. Менять `memory_free()` на API со статусом прямо сейчас

Не выбрано в рамках этого Critical-пункта. Явный `memory_status_t` был бы лучше
для сообщения об ошибке coalesce или invalid pointer, но меняет публичный API и
относится к будущему переходу на context-based allocator. Текущий контракт
сохранён: `memory_free()` при внутренней невозможности вычисления возвращается
без записи metadata.

### 6.7. Одновременно реализовать защиту от double free и forged pointer

Не выбрано намеренно. Это третий самостоятельный Critical-пункт. Он потребует
обхода списка с проверкой физической непрерывности и статусов ошибок. Простая
проверка переполнения не доказывает, что указатель действительно является
payload занятого блока.

## 7. Влияние изменения

### 7.1. Потребление памяти

**RAM:** постоянный размер heap остаётся 2048 байт. Новые локальные `size_t` и
`bool` живут на стеке только во время `memory_alloc()`/`memory_free()`; они не
добавляют metadata в heap и не уменьшают доступный payload. Пиковый стек этих
функций может немного увеличиться из-за временных переменных для проверенных
размеров. На TC397XA это следует учесть в общем stack budget, но рост мал и
фиксирован.

**Flash/code size:** добавляется несколько небольших helper-функций и ветвей.
Компилятор может встроить `add_sizes()`/`block_total_size()` в release-сборке,
но это зависит от флагов HighTec. Точный рост flash необходимо измерить на
целевом toolchain; он не требует таблиц, буферов или динамической памяти.

### 7.2. Производительность

Allocation получает несколько арифметических проверок до обхода списка:
остаток от деления при выравнивании, вычитание из `SIZE_MAX`, сравнение и
обычное сложение. Split выполняет ещё один проверенный расчёт. Free получает до
двух проверенных расчётов — по одному на каждого соседа при coalesce.

Это небольшой постоянный overhead. Доминирующая стоимость `memory_alloc()`
осталась прежней: first-fit проходит список блоков и имеет O(n) в худшем случае.
Новых циклов в hot path, кроме уже существующего обхода списка и побайтного
копирования header, не введено.

На 32-битном TriCore сравнение и сложение `size_t` обычно являются простыми
32-битными операциями. Фактические такты, размер сгенерированного кода и влияние
оптимизации необходимо подтвердить через `tricore-gcc` и измерение на TC397XA.

### 7.3. Детерминированность

Новые проверки имеют фиксированное число инструкций и условных переходов; нет
heap allocation, вызовов ОС, блокировок или повторных попыток. Поэтому они не
меняют асимптотическую сложность и не вводят неконтролируемую задержку.

Путь ошибки обычно даже короче: переполняющий запрос отклоняется до поиска
списка. Нормальный путь получает небольшой постоянный overhead. Аллокатор всё
ещё не имеет строгой hard-real-time гарантии, так как first-fit поиск остаётся
O(n), а будущая строгая валидация указателей может добавить собственный обход
списка.

### 7.4. Переносимость на AURIX TC397XA

Решение не содержит platform-specific кода. Оно опирается на C99 (`size_t`,
`SIZE_MAX`, сравнения и `bool`) и поэтому одинаково применимо к host и к
HighTec GNU TriCore compiler.

На 32-битном AURIX `size_t` обычно имеет меньший диапазон, чем на 64-битном
host, поэтому переполнение достижимо при меньших числах; именно поэтому
предикаты особенно важны. Они не требуют 64-битной арифметики, libc или
расширений GCC и не меняют контракт `TRICORE_TARGET`/`MEMORY_ALLOCATOR_ALIGNMENT`,
введённый предыдущим пунктом.

Target-прогон всё равно обязателен: host-тесты доказывают логику на host ABI, но
не заменяют сборку строгими предупреждениями и выполнение smoke-тестов через
`tricore-gcc` с целевыми ABI-флагами.

## 8. Проверка

В `tests/test_memory_allocator_alignment.c` добавлены следующие регрессии:

1. `memory_alloc(SIZE_MAX)` возвращает `NULL`;
2. `memory_alloc(SIZE_MAX - 1U)` возвращает `NULL` для используемого alignment;
3. после каждого отказа `memory_alloc(64U)` успешно работает, то есть отказ не
   изменяет heap;
4. `memory_free(NULL)` не нарушает состояние; после освобождения обычного блока
   allocator способен снова выделить крупный блок после coalesce.

Для воспроизводимого запуска в корне проекта добавлен GNU Makefile:

```sh
make test-host CC=clang
make test-sanitize CC=clang
make test-host CC=gcc
make target-debug
make target-release
```

Первые три команды успешно выполнены в host-окружении. `target-debug` и
`target-release` формируют команды для `tricore-gcc`; целевой toolchain в данном
окружении отсутствует, поэтому сборка и запуск на TC397XA остаются обязательной
следующей проверкой.

## 9. Что это изменение намеренно не решает

Пункт закрывает переполнения размеров и `memory_free(NULL)`, но не делает
`memory_free()` безопасным для произвольного ненулевого указателя. В частности,
ещё не реализованы полноценные проверки против:

- double free;
- forged pointer;
- interior pointer;
- повреждённых полей `next`/`prev` и metadata после пользовательского overflow.

Это следующий Critical-пункт backlog. Его нельзя считать закрытым только
потому, что арифметика размеров теперь проверяется: для него нужны явная
валидация принадлежности payload текущему занятому элементу списка, инварианты
списка и предпочтительно API со status code.
